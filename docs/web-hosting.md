# Hosting the OpenWord website build

The website build is a static site. There is no server component: documents never leave the browser, and every request after first load is a same-origin asset fetch.

## Build

1. Build or install the Writer runtime into `public/writer-runtime/` first:

   ```sh
   npm run engine:build
   ```

   Alternatively, install a verified prebuilt runtime into `public/writer-runtime/`. The build is incomplete without it: the runtime host verifies `runtime-manifest.json` (byte lengths and SHA-256 hashes) before starting.

2. Build the site:

   ```sh
   npm run build:web
   ```

   Output lands in `dist-web/`. Deploy that directory as-is. The runtime assets are large (hundreds of MB, dominated by `soffice.wasm` and `soffice.data`), so account for artifact-size limits on your host.

## Deploying to Cloudflare Workers and R2

This is the reference deployment. The shell ships as Workers static assets and the Writer runtime is served from R2 by a Worker on the same origin.

Two constraints rule out the obvious alternatives:

- **Static hosts cap file size.** Cloudflare Pages and Workers static assets both reject any single file over 25 MiB; GitHub Pages caps a file at 100 MB and a site at 1 GB. `soffice.wasm` and `soffice.data` are far larger, so the runtime cannot ship as static assets anywhere.
- **The runtime must be same-origin.** `runtimeAssetUrl()` in `src/writer/runtimeHost.ts` rejects any runtime base URL carrying a scheme or protocol-relative prefix, and threaded LOWA needs cross-origin isolation. Pointing the app at a public R2 domain would therefore fail, and would additionally require `Cross-Origin-Resource-Policy: cross-origin` plus a CORS policy. The Worker proxies R2 instead, so the browser only ever sees one origin.

R2 also bills no egress, which matters when every cold visit downloads the whole runtime.

### One-time setup

```sh
npx wrangler@4 login
npx wrangler@4 r2 bucket create openword-writer-runtime
```

The bucket name lives in `wrangler.toml` under the `WRITER_RUNTIME` binding; `scripts/deploy/upload-writer-runtime.mjs` reads it from there, so change it in one place.

### Publishing

```sh
npm run deploy:runtime   # verify and upload public/writer-runtime/ to R2
npm run deploy:web       # build:web, prepare dist-web/, then wrangler deploy
```

`deploy:runtime` re-hashes every file against `runtime-manifest.json` before sending anything, so a runtime that does not match its own manifest cannot be published. It uploads the manifest last, because the service worker treats a changed manifest body as the signal to drop its runtime cache.

`deploy:web` runs `scripts/deploy/prepare-web-deploy.mjs`, which writes a `.assetsignore` into `dist-web/` excluding `writer-runtime/`. Without it the deploy fails with `Asset too large`, because Vite copies `public/` verbatim into the build output.

### Large runtime files

Wrangler uploads at most 315 MB per object and one object at a time. `soffice.data` can exceed that. When it does, `deploy:runtime` stops before uploading anything and tells you to re-run through an S3-compatible client:

```sh
npm run deploy:runtime -- --tool rclone --remote r2
```

Configure the `r2` remote first — see [Cloudflare's rclone guide](https://developers.cloudflare.com/r2/examples/rclone/). `--dry-run` prints the commands without running them.

### Headers

`public/_headers` carries the isolation headers and is copied into `dist-web/` by the build. It applies only to static asset responses; Cloudflare never applies it to responses generated by Worker code, so `worker/index.ts` sets the same headers on everything it returns from R2.

Runtime files are served `public, max-age=0, must-revalidate` rather than `immutable`. Their names are stable across engine builds, so an immutable entry would pin a browser to bytes that no longer match `runtime-manifest.json` after an upgrade, and the runtime host refuses to start on a hash mismatch. Revalidation costs a 304 against the R2 ETag, and the service worker's own cache means repeat visits do not reach the network at all.

The Worker supports range requests (`soffice.data` may be range-requested) and conditional requests, and returns 206 and 304 accordingly.

## Required headers

Writer is threaded WebAssembly and requires `SharedArrayBuffer`, so every document response must be cross-origin isolated. The runtime host refuses to start otherwise. Serve all responses with:

- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Embedder-Policy: require-corp`
- `Cross-Origin-Resource-Policy: same-origin`
- `X-Content-Type-Options: nosniff`

and serve `.wasm` files with the `application/wasm` MIME type (required for streaming compilation).

### nginx

```nginx
server {
    root /srv/openword/dist-web;

    types {
        application/wasm wasm;
    }

    add_header Cross-Origin-Opener-Policy "same-origin" always;
    add_header Cross-Origin-Embedder-Policy "require-corp" always;
    add_header Cross-Origin-Resource-Policy "same-origin" always;
    add_header X-Content-Type-Options "nosniff" always;
}
```

### Caddy

```caddyfile
example.com {
    root * /srv/openword/dist-web
    file_server

    header {
        Cross-Origin-Opener-Policy "same-origin"
        Cross-Origin-Embedder-Policy "require-corp"
        Cross-Origin-Resource-Policy "same-origin"
        X-Content-Type-Options "nosniff"
    }
}
```

Caddy serves `.wasm` as `application/wasm` by default.

### Netlify (`_headers` file in the publish directory)

```
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  Cross-Origin-Resource-Policy: same-origin
  X-Content-Type-Options: nosniff
```

Netlify serves `.wasm` as `application/wasm` by default.

### Hosts that cannot set headers

Static hosts without header control (for example GitHub Pages) still work, provided they can hold the runtime at all — see the file-size caps noted above. `openword-sw.js` re-serves every response with the isolation headers injected by a service worker. The cost is one automatic reload on the first visit, so the page can come back under service-worker control with the injected headers. Subpath hosting (`https://user.github.io/openword/`) is supported; all asset URLs are relative.

## Offline behavior

The service worker caches on use with the Cache API: the app shell and the Writer runtime are stored as they are first fetched. The first visit downloads the multi-hundred-MB runtime; subsequent visits, including fully offline ones, are served locally. Runtime assets are cached cache-first (they are content-addressed by the runtime manifest's hashes); `runtime-manifest.json` and navigations are network-first so updates propagate, with cache fallback offline.

## Browser support

| Browser | Editing | Document storage and saving |
| --- | --- | --- |
| Chromium (Chrome, Edge) | Full | Full, including File System Access API save-in-place to local files |
| Firefox | Full | Browser-storage documents, download-based export |
| Safari | Full | Browser-storage documents, download-based export |

All browsers must support `SharedArrayBuffer` under cross-origin isolation; every current release of the above does.

## Privacy

There is no server storage. Documents live in browser storage (OPFS/IndexedDB) or in local files the user explicitly picks. After the site loads, it makes no network requests beyond fetching its own same-origin assets.
